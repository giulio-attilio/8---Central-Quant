4. NORMATIVE-DIFFERENCE TRACEABILITY

4.1 Final-document authority

The header, authority clause, and revision history are required to promote the
document. They state that V2.3 supersedes V2.2 for future specification work,
V2.2 remains immutable historical evidence, the implementation phase remains
V2.3 Migration Auditor Dry-Run, and promotion grants no code/runtime/broker/

4.2 Three factual identities and request identity

Section 4.3/4.3A adds the precise distinction:

- signal_id: one factual productive Falcon signal birth;
- decision_request_id: one factual decision evaluation request; and
- decision_id: one factual durably completed ALLOW/DENY result for that exact
  request.

It maps to base amendment 1 and is constrained by Review2/Review3. It prohibits
substitution with execution/lifecycle/logical/client/broker/exchange/fill/
position/broker-derived identity. Request issuance, provenance, explicit retry,
restart-new-evaluation, digest, signal binding, and non-reuse map to base
4.3A.2, Review2 4.3A.8C, and Review3 corrections 1–3.

4.3 One narrowly authoritative store and same-store claim

Section 4.3A authorizes exactly one future dedicated provider-owned
DECISION_IDENTITY_RECORD_STORE. Its authority is only request/result identity
and exact request/signal correlation. It is not Registry V1/V2, generic
persistence, execution, risk, broker, financial, position/ownership, or
execution-intent authority.

The same section maps Review3 correction 1 verbatim in substance: one lineage
per request ID; durable CLAIMED and COMPLETED only; completed as terminal form
of same claim/key; approved minimum claim material; no physical/broker/Registry/
ownership/financial/execution-intent identity; and no second store or V2.7A.3.

4.4 Ordering, failure, incomplete, crash, and concurrency

The final ordering is exactly: create request ID; canonical request/digest with
exact signal; serialize actual provider/store domain; check state/digest; commit
claim if absent; only then associate V2.7A identity; run unchanged V1 provider
semantics; create candidate completed material; durable COMPLETED/validate; then
expose factual decision_id/POST.

Base durability text, Review2's single-evaluation and historical replay
correction, and Review3's durable witness correction jointly map:

- identity failure preserves existing V1 current decision behavior only;
- V2.7A identity/POST fails closed;
- CLAIMED-without-COMPLETED is IDENTITY_REQUEST_INCOMPLETE, not third state;
- four crash cases are explicit;
- same ID/different digest conflicts;
- same ID/same digest/CLAIMED has no second identity evaluation;
- same ID/same digest/COMPLETED is historical-only;
- exactly one lineage and at most one completed record exist;
- actual topology serialization is mandatory and in-process-only locking is
  insufficient for multi-process writers; unable proportional serialization
  stops implementation for architecture review.

4.5 Replay/exposure/exact correlation

Review2 correction 2 maps the final read-only historical IDENTITY_REPLAY
contract. Historical ALLOW/DENY cannot become current allowed/denied value,
short-circuit can_open_trade_decision, bypass risk, change Falcon control flow,
authorize execution, or provide stale approval. A current decision is
NEW_REEVALUATION with a new request ID.

Review2 correction 3 and Review3 correction 3 map decision_id exposure: a
candidate can exist internally but is factual/external only after durable
COMPLETED validation. Exact correlation remains:
completed_record.signal_id == canonical_decision_request.signal_id ==
paired_POST_DECISION.signal_id. No symbol/setup/side/logical/legacy/uncorrelated
fallback is retained.

4.6 V2.7A table, substeps, I/O, and activation
