2. CURRENT V1 FAILURE

2.1 Modelo V1 confirmado

trade_registry.py V1 usa trade_id determinístico:
BOT:SETUP:SYMBOL:SIDE.

open_trades é um dict indexado por essa chave. register_open_trade grava diretamente em open_trades[trade_id]. lifecycle_id, client_order_id e broker_order_id podem estar presentes no payload, mas não fazem parte da chave física. Assim, duas execuções legítimas iguais em bot/setup/symbol/side colidem e a segunda pode sobrescrever a primeira.

Exemplo:
- FALCON / FALCON15 / SOLUSDT / LONG / lifecycle A
- FALCON / FALCON15 / SOLUSDT / LONG / lifecycle B

Ambas geram FALCON:FALCON15:SOLUSDT:LONG. V1 não mantém duas rows abertas. update_trade e close_trade genéricos selecionam por trade_id; expected_identity existe em partes de close, mas não é exigido universalmente.

2.2 Outros limites V1

- logical trade_id é usado como selector mutante por Falcon, Turtle, Predator, Donkey, TrendPro, Cobra, Meme e sincronizadores de main.py.
- Donkey tenta uma lista de setup-derived IDs em update/close, podendo aceitar o primeiro match.
- main.py possui sincronizadores e alguns writers diretos de snapshot que usam assinatura lógica/fallback manual.
- V1 mode inference pode deixar PAPER persistido apesar de evidência factual broker.
- RLock é somente intra-processo; não há protocolo WAL, generation, checksum transacional, operação idempotente autoritativa nem lock interprocesso.
- closed_trades é lista histórica e parte dos consumers trabalha com aliases legados.
- Falcon já propaga lifecycle_id e IDs fortes em diversos caminhos, mas V1 ainda persiste fisicamente por chave lógica.
- Posição MANUAL/EXTERNAL é detectada por Falcon/Main como não gerenciada, mas V1 genericamente não impede chamada malformada que tente registrá-la como Falcon.

2.3 Consequência que V2.1 corrige

V2.1 substitui a identidade física por execution_id, que é o mesmo valor do lifecycle operacional. logical_trade_id é preservado apenas para agrupamento, analytics, compatibilidade e lookup read-only quando unívoco. Nenhuma mutação V2 escolhe row por logical_trade_id, symbol/side, preço médio, timestamp aproximado ou primeira/última ocorrência.

3. FINAL V2 PRINCIPLES

P-01. Uma execução Central possui uma única identidade física e operacional: execution_id == lifecycle_id.
P-02. logical_trade_id pode agrupar N execuções; nunca é chave física de open trade.
P-03. Uma ordem/fill factual pertence a no máximo uma execução.
P-04. Retry idêntico é idempotente; retry com digest material divergente é conflito.
P-05. Mutation sem execution_id exato, ou com identidade esperada divergente, falha fechada.
P-06. Nenhuma seleção mutante usa symbol/side, preço médio agregado da corretora, setup alternativo ou heurística temporal.
P-07. Broker é executor/custodiante e fonte factual de ordem, fill, fee e funding; não define ownership Central.
P-08. Entry/exit/PnL por robô provêm de fills/ordens da execução correspondente, não de média agregada broker.
P-09. Estado fechado nunca reabre. Reconciliação financeira posterior acrescenta fato versionado sem trocar lifecycle.
P-10. TP50 é partial close; runner continua na mesma execution_id.
P-11. MANUAL_EXTERNAL é observação read-only e não pode ser adotada, fechada, protegida ou usada como fill Central.
P-12. PAPER, VERIFY e LIVE têm contratos distintos. Evidência broker contraditória gera MODE_CONFLICT, não promoção silenciosa.
P-13. Journal EVENT_COMMITTED é autoridade de idempotência; snapshot é estado material; operation_ledger é cache.
P-14. Snapshot/journal inválidos bloqueiam mutations até recovery determinístico.
P-15. V1 archive e legacy views nunca se tornam source de mutation.
P-16. Nenhuma fase V2.0–V2.10 habilita write LIVE.
P-17. O caminho Falcon continua único: Execution Orchestrator/Execution Engine/Broker/Lifecycle existentes; V2 não cria segundo executor.

4. CANONICAL IDENTITY CONTRACT

4.1 Identidade única

execution_id é a identidade canônica de cada execução V2. lifecycle_id é seu alias operacional de compatibilidade e possui exatamente o mesmo valor.

Payload rules:
- Se só execution_id é fornecido, lifecycle_id é projetado com o mesmo valor.
- Se só lifecycle_id é fornecido em adapter compatível, ele é aceito como execution_id somente quando a chamada é permitida pelo modo/legado e o valor é preservado.
- Se ambos são fornecidos e não são exatamente iguais após trim seguro, retornar REGISTRY_EXECUTION_LIFECYCLE_ID_CONFLICT; mutated=false.
- Nenhum caller pode criar, regenerar, converter ou mapear um segundo ID.
- A row canônica armazena execution_id; lifecycle_id pode ser serializado como alias durante a janela de compatibilidade, com invariant de igualdade.

4.2 Geração de ID

Função canônica conceitual:
generate_execution_lifecycle_id()

Formato:
exec_<uuid4 lowercase>

Exemplo:
exec_9c8e4f1b-1e2b-4acf-ae12-442a6ca85e7e

Razão do formato:
- Python runtime declarado em runtime.txt é python-3.11.9.
- uuid.uuid7 não está disponível na biblioteca padrão dessa versão.
- uuid.uuid4 usa aleatoriedade do sistema, não exige dependência externa e não depende de símbolo, lado, preço ou timestamp isolado.
- Ordenação cronológica é fornecida por created_at, journal event_seq e generation, não pelo formato do ID.
- Consumers devem tratar o valor como opaco.

4.3 Quem gera e quando

Execution Orchestrator é o owner da geração para LIVE. Um shared pure identity helper é usado por adapters PAPER. Bot, broker, Registry reader, reconciliador e projection nunca geram substituto depois do boundary.

Ordem:
1. signal_id e decision_id autorizam uma nova tentativa.
2. Orchestrator chama generate_execution_lifecycle_id uma vez.
3. Execution Intent recebe execution_id/lifecycle_id iguais e intent idempotency key.
4. Registry V2 grava EVENT_PREPARED/ENTRY_INTENT e retorna sucesso somente após EVENT_COMMITTED; esse é o durable Registry boundary.
5. Lifecycle/History projection recebe o mesmo ID; se a projeção necessária à segurança falhar, broker submit não inicia.
6. Só então é criado/reservado client_order_id e ocorre o boundary mutável de broker.
7. ACK, order IDs, fills, disaster stop, TP50, close e reconciliation usam o mesmo ID.

Factual Falcon signal and decision identity for V2.7A/V2.8
-----------------------------------------------------------

For Falcon V2.7A/V2.8 observation, signal_id is a factual signal-birth
identity, decision_request_id is a factual decision-evaluation-request
identity, and decision_id is a factual completed-decision-result identity.
None is generated, substituted, repaired, or correlated by the VERIFY observer.
VERIFY observation does not create operational execution_id or lifecycle_id and
does not change existing LIVE ordering for execution intent or broker submit.

signal_id MUST:

- be born at factual productive Falcon signal birth;
- be stable for the same factual signal and retry;
- be distinct for distinct legitimate signals and reentries;
- be independent of broker response and physical order/fill/position identity;
- have defined restart/retry semantics;
- be versioned and accompanied by signal_identity_version and
  signal_identity_provenance;
- not be legacy sig.id unless semantic identity equivalence is proved; and
- not be logical_trade_id, execution_id, lifecycle_id, client_order_id, or a
  broker/exchange/fill identity.

The implementation contract must define and test the exact signal_id
derivation/issuance material before productive use. This specification does
not prescribe UUID versus deterministic hashing without repository evidence.
If a persistence-safe restart/retry/reentry contract cannot be established,
implementation must stop and return to architecture review.

decision_id MUST:

1. identify one factual completed decision result;
2. be non-empty for a completed POST_DECISION ALLOW or DENY;
3. be immutable after that decision result is issued;
4. remain identical when the same factual decision result is transported,
   replayed, retried, logged, or propagated;
5. differ for a genuinely new or re-evaluated decision result;
6. not be signal_id, decision_request_id, execution_id, lifecycle_id,
   logical_trade_id, client_order_id, broker_order_id, exchange_order_id,
   fill_id, position identity, or broker-derived identity;
7. not be generated by the V2.8 observer, a VERIFY fallback, or an unrelated
   consumer; and
8. carry versioned factual provenance.

Before a factual completed decision exists, decision_id is absent or None and
the observation is PRE_DECISION only. A response presented as completed but
lacking decision_id is decision-identity unavailable, cannot qualify as
POST_DECISION, and blocks V2.7A exit; it receives no fabricated fallback.

Decision-to-signal correlation:

- A completed POST_DECISION result MUST have factual provenance sufficient to
  prove it belongs to the exact factual signal_id of its paired PRE_DECISION
  observation.
- The result MUST be bound to that exact signal_id. Transport or replay of the
  same result MUST retain that same binding.
- A decision issued for signal A MUST NOT qualify as POST_DECISION for signal
  B. Same symbol, setup, economic side, logical_trade_id, legacy sig.id, or an
  uncorrelated decision_id is not sufficient correlation.
- The V2.7A implementation dossier MUST select, document, and test one exact
  factual correlation mechanism. It may use signal_id returned in the
  completed decision response, decision_request_id, request digest, or another
  immutable provider-issued provenance mechanism; this specification does not
  prescribe a field name without repository evidence.
- A failed, missing, mismatched, or stale correlation MUST fail paired
  POST_DECISION qualification and remain a factual correlation conflict. It
  must not be repaired by symbol/side matching, a legacy alias, or a new ID.

4.3A FACTUAL DECISION REQUEST AND COMPLETED DECISION IDENTITY FOR V2.7A

4.3A.1 Three distinct facts

For V2.7A observation, these facts are separate and no field may substitute
for another:

1. signal_id identifies one factual productive Falcon signal birth.
2. decision_request_id identifies one request/evaluation of that signal by the
   factual Central decision provider.
3. decision_id identifies one factual durably completed ALLOW or DENY result
   for that exact decision_request_id.

decision_request_id and decision_id MUST NOT be signal_id, execution_id,
lifecycle_id, logical_trade_id, client_order_id, broker_order_id,
exchange_order_id, fill_id, position identity, or broker-derived identity.
None depends on broker, Registry V1, Registry V2, physical order, fill, or
position state for issuance.

4.3A.2 decision_request_id contract

decision_request_id is required for a V2.7A identity-qualified decision
evaluation. The exact factual caller creates it before invoking the factual
Central provider. It MUST identify exactly one factual evaluation request; be
opaque, cryptographically random, versioned, and issued once per genuine new
evaluation; not be a deterministic hash of signal/economic inputs; belong to
exactly one signal_id; remain byte-identical only for explicit transport/retry
of that same evaluation; differ for every genuinely new/re-evaluated decision
even where inputs and ALLOW/DENY coincide; carry versioned provenance; and
never be inferred, regenerated, repaired, or substituted by the provider,
observer, broker, Registry, or consumer.

The implementation dossier must define exact opaque format, random source,
validation, version, issuer seam, and in-process retry retention. It MUST NOT
derive this ID from legacy sig.id, signal_id, timestamp alone, or market/broker
facts. Restart without an explicitly preserved request ID is NEW_REEVALUATION,
not replay: the next invocation receives a new decision_request_id. Matching
signal_id or request values never prove replay.

The issuer NEVER intentionally reuses a decision_request_id. Retention expiry
can make historical identity projection unavailable; it never makes an old ID
eligible for reuse. A cryptographic collision against retained identity
evidence is a conflict, never overwrite or reuse.

4.3A.3 DECISION_IDENTITY_RECORD_STORE: narrow authority

There is one and only one dedicated provider-owned
DECISION_IDENTITY_RECORD_STORE implementation that may later be authorized
under V2.7A.2. It is narrowly authoritative only for decision request/result
identity and exact request/signal correlation.

It is NOT Registry V1, Registry V2, Registry mutation authority, execution
authority, risk-policy authority, broker authority, financial truth,
position/ownership authority, or execution-intent persistence. It cannot
independently determine whether a trade executes. No generic persistence
authority, second store, shared persistence framework, or alternate store is
created.

A completed record is uniquely keyed by decision_request_id. Its minimum
immutable material is record_schema_version and integrity/version material;
decision_request_id, request identity version, and issuer provenance; exact
signal_id; decision_id; literal decision_result ALLOW/DENY and compatible
allowed boolean; decision identity version/provenance; decision-request digest
version and canonical digest; decision-to-signal correlation method/version and
evidence; completed_at; and factual provider/function/version plus applicable
policy/risk provenance.

The canonical request digest is calculated over a versioned canonical
representation of all material request facts supplied to the provider,
including exact signal_id. It excludes decision_id and all execution,
lifecycle, broker, exchange, fill, Registry, and physical identities. The
implementation dossier defines the exact canonical representation before use.

The record must not create, contain as authority, or infer execution_id,
lifecycle_id, client/broker/exchange order IDs, fills, position ownership,
financial truth, or execution intent. It is not a position record and cannot
adopt MANUAL_EXTERNAL or EXTERNAL exposure.

4.3A.3A DECISION_REQUEST_CLAIM IN THE SAME STORE

DECISION_IDENTITY_RECORD_STORE contains one request lineage per
decision_request_id. Before an evaluation may be associated with V2.7A identity
preparation, that lineage MUST have one valid durable
DECISION_REQUEST_CLAIM. The claim is not a second store, Registry record,
execution intent, risk decision, broker record, financial record, or ownership
record. It is durable evidence only that one exact request ID was claimed for
one exact factual canonical request.

The only durable lineage states are:

- CLAIMED: a valid durable request claim exists but no valid durable completed
  decision record exists; and
- COMPLETED: the same request lineage/key has a valid durable completed
  decision record.

COMPLETED is the terminal materialized form of the same claim/key. There is no
third durable state, independent claim authority, additional lifecycle, or
additional V2.7A substep.

Minimum immutable claim material is claim_schema_version and claim
integrity/version material; decision_request_id; decision-request identity
version and issuer provenance; exact signal_id; canonical request digest and
digest version; claim state; claimed_at; and issuer/provider provenance
sufficient to identify factual request and provider boundary.

The claim MUST NOT include execution_id, lifecycle_id, client_order_id,
broker/exchange order IDs, fill IDs, position ownership, financial facts, or
execution intent. Its sole authority remains one decision request/result
identity lineage and exact signal/request correlation. Once valid durable
CLAIMED exists for request X, X is never treated as unseen again.

4.3A.3B Claim ordering and legacy equivalence

For a V2.7A identity-qualified evaluation, the required factual order is:

1. caller creates one new random opaque decision_request_id;
2. canonical request and digest are formed, including exact signal_id;
3. store serializes the request over the actual provider/store concurrency
   domain;
4. durable state is checked and exact digest consistency verified;
5. if no state exists, durable DECISION_REQUEST_CLAIM is committed;
6. only then may provider evaluation be associated with V2.7A identity;
7. provider executes unchanged current V1 risk semantics;
8. completed ALLOW/DENY creates candidate decision_id/record material;
9. completed record is durably committed and validated as COMPLETED; and
10. only then may decision_id be factual/external POST_DECISION identity.

Identity persistence is never a prerequisite for legacy V1 decision behavior.
Claim write failure, claim conflict, incomplete claim, completed-record write
failure, corrupt record, missing replay record, or signal-binding mismatch MUST
NOT prevent or alter the current can_open_trade_decision evaluation that would
otherwise occur. It executes with unchanged V1 semantics. The additive V2.7A
identity state is unavailable/conflicted, decision_id is absent/None, and
POST_DECISION is blocked. This preservation of V1 behavior is not general
execution fail-open and never makes a risk-control short circuit.

4.3A.3C Incomplete request

IDENTITY_REQUEST_INCOMPLETE is the one derived identity status for a valid
durable CLAIMED lineage without valid COMPLETED. It includes a claim left after
restart or verified absence of an active completion owner. It is not a third
durable state, lifecycle, or execution status.

It has no factual decision_id, cannot qualify as POST_DECISION, cannot support
historical replay, cannot contribute to V2.7A exit, and does not alter current
V1 risk decision behavior. A caller needing a correctly formed current V2.7A
identity evaluation uses NEW_REEVALUATION and a new decision_request_id.

4.3A.4 Durability and failure boundary

A V2.7A identity-authoritative completed result exists only after the
provider-owned record is durably COMPLETED and passes validation. A
pre-existing provider response remains a valid legacy V1 ALLOW/DENY even where
identity recording fails.

For all identity failures -- claim write failure, claim conflict, incomplete
claim, completed-record write failure, corrupt record, missing replay record,
or signal-binding mismatch -- existing V1 decision behavior remains unchanged.
That is the sole meaning of FAIL OPEN V1. It does not allow execution, broker,
risk, or safety failure to fail open. V2.7A identity fails closed: no factual
decision_id, no POST_DECISION qualification, and no V2.7A exit based on that
request.

Conceptual additive identity statuses include IDENTITY_RECORD_WRITE_FAILED,
IDENTITY_RECORD_CONFLICT, IDENTITY_RECORD_CORRUPT,
IDENTITY_RECORD_NOT_FOUND, and IDENTITY_REQUEST_INCOMPLETE. They are not
Registry statuses and never fabricate decision_id, repair correlation, change
V1 risk/sizing/PAPER/LIVE, or create execution authority.

4.3A.5 Exact decision-to-signal binding

For a V2.7A completed decision, safe-trimmed, canonically validated values
MUST satisfy:

completed_record.signal_id
  == canonical_decision_request.signal_id
  == paired_POST_DECISION.signal_id

Returned additive metadata preserves exact record/request/signal correlation
evidence and method/version. Symbol, setup, economic side, logical_trade_id,
legacy sig.id, timestamps, or uncorrelated decision_id are never substitutes.
Mismatch, absence, stale reentry, or corrupt evidence is a factual correlation
conflict and cannot qualify as POST_DECISION.

4.3A.6 READ-ONLY HISTORICAL IDENTITY PROJECTION; NO RISK OR EXECUTION REPLAY

IDENTITY_REPLAY is READ-ONLY HISTORICAL IDENTITY PROJECTION. It exists only
when the same explicit decision_request_id, same canonical request digest, and
one valid durable COMPLETED record are present. It may project only historical
factual metadata: request ID, decision ID, exact signal binding, stored
completed ALLOW/DENY as evidence, identity/provider provenance, integrity, and
identity status.

Stored ALLOW/DENY is historical evidence only. IDENTITY_REPLAY MUST NOT become
the current allowed/denied value; short-circuit can_open_trade_decision or any
current provider; bypass current risk evaluation; alter Falcon control flow;
authorize execution or be passed to Execution Orchestrator as current approval;
provide stale operational approval; or change risk, sizing, PAPER, LIVE,
broker, Registry, or ownership semantics.

The productive current-decision path continues to evaluate as before V2.7A.
Store lookup cannot substitute for evaluation otherwise required for a current
decision. Only additive identity/provenance/status may differ, preserving
PREEXISTING_FIELD_VALUE_EQUIVALENCE. A caller requiring a CURRENT decision MUST
use NEW_REEVALUATION, a new request ID, current provider evaluation, and a new
decision_id only after durable completion. No operational response replay is
authorized.

4.3A.7 Conflict, duplicate, and single-evaluation owner

For request X:

- same X with different canonical digest is immediate
  DECISION_REQUEST_ID_CONFLICT; it never joins, replaces, merges, overwrites,
  or silently selects a lineage;
- same X/same digest/valid CLAIMED must not create a second V2.7A
  identity-associated evaluation or second decision candidate;
- same X/same digest/valid COMPLETED supports historical identity projection
  only; and
- exactly one request lineage and at most one authoritative COMPLETED record
  may exist for X.

While a real active completion owner is known inside a safe serialization
boundary, a same-X/same-digest participant may wait and re-check committed
state. After restart it MUST NOT assume an owner remains active. A durable
CLAIMED record without COMPLETED is incomplete, neither replayable nor new.

This forbids a second V2.7A identity-associated evaluation, not an ordinary
current V1 provider evaluation. If productive current path is invoked, it
retains ordinary current risk evaluation and returns no V2.7A completed
identity for consumed/incomplete ID. A correctly formed new V2.7A current
evaluation mints a new request ID.

4.3A.8 Actual concurrency-domain serialization

Serialization/single-flight MUST cover the actual concurrency domain of the
factual provider and selected store. If multiple process, workers, or threads
can access provider/store, it MUST prevent duplicate completion ownership across
that shared-writer domain. In-process-only lock is insufficient whenever
multiple provider processes can access the same store.

This specification does not require storage technology, a thread, a network
coordinator, generic persistence service, or Registry V2 WAL. If selected store
cannot provide proportional cross-writer serialization in actual deployment
topology, implementation MUST STOP for architecture review.

4.3A.8A Claim-aware crash semantics

A. Crash before durable CLAIMED commit

No identity claim exists. V1 is unaffected. If retry finds no factual evidence
that a claim committed, identity preparation may start as normal first claim
for the same ID under atomic store rules.

B. Crash after CLAIMED before provider evaluation completes

The ID is durably known as claimed/incomplete. After restart it MUST NOT start
a new V2.7A identity-associated evaluation under that ID. It is
IDENTITY_REQUEST_INCOMPLETE, has no factual decision_id and no POST_DECISION.
A current V2.7A evaluation needs NEW_REEVALUATION and a new ID.

C. Provider result exists but crash before COMPLETED commit

The same B rule applies. Valid CLAIMED proves a consumed/incomplete request,
not factual completed identity. No candidate or stale ALLOW identity is
externally factual. New current identity-qualified evaluation needs new ID.

D. Crash after valid durable COMPLETED commit

Exact completed record may be read under the historical projection rule. It
never substitutes for current risk evaluation or execution approval.

4.3A.8B Exposure and store safety

Candidate decision_id may exist internally as record material but MUST NOT be
external/factual until same lineage is durably COMPLETED and validation passes.
On claim/write/incomplete/conflict/corruption/missing-replay/binding failure,
external decision_id is absent or None, identity unavailable, and
POST_DECISION blocked.

Before implementation, dossier must prove the single dedicated store provides
atomic durable claim/complete before identity exposure; unique serialized lookup
by request ID; same-key/same-digest validated behavior; different-digest
conflict; restart validation of schema/integrity/request/digest/signal binding;
explicit corrupt-record handling without silent repair; bounded retention with
documented horizon and non-reuse/conflict protection; and no broker, exchange,
network, Registry V1/V2, or runtime-execution dependency.

The store need not and must not copy Registry V2 WAL beyond proportional
atomicity, integrity, restart, duplicate, and conflict guarantees needed for
this narrow authority. Existing append-only decision_log telemetry is not this
store and cannot become it without separate architecture review.


4.4 Restart e retry

Antes de broker invocation, a identity é durável no intent/Registry committed. Depois de broker invocation, ela nunca é regenerada. Registry persistence failure reutiliza a mesma identity e idempotency key. ACK perdido reconcilia client_order_id/broker order/fill sob a mesma execution_id. Lifecycle projection faltante é reconstruída do journal committed; não cria outra identity.

Se intent/lifecycle persistence falhar antes do Registry commit, não há broker submit. Se Registry commit falhar, não há sucesso de entry intent e não há broker submit. Se uma falha ocorrer depois de broker invocation, recovery deve consultar a mesma identity/client order e reconciliar antes de qualquer retry.

4.5 PAPER, LIVE, VERIFY e legacy

LIVE:
- execution_id/lifecycle_id iguais são obrigatórios.
- são gerados antes de client_order_id e broker submit.
- signal_id, decision_id, owner_type=CENTRAL, position_side e execution intent idempotency key são obrigatórios.

PAPER:
- uma posição PAPER Central gerenciada recebe execution_id/lifecycle_id iguais ao nascer.
- nenhuma broker ID é obrigatória.
- signal_id/decision_id podem ser null somente para adapter legado, marcado LEGACY_MISSING.

VERIFY:
- não cria execution Registry aberta, execution_id operacional ou lifecycle_id operacional;
- pode expor observação de plano read-only e não operacional em exatamente dois
  shadow stages: PRE_DECISION ou POST_DECISION;
- PRE_DECISION -> POST_DECISION é enriquecimento observacional do mesmo plano
  VERIFY, não mutação de lifecycle de execução nem transição de registry_mode;
- conversão VERIFY -> PAPER/LIVE cria nova identity; não muta modo de um plano VERIFY; e
- nenhum stage fabrica signal_id, decision_request_id, decision_id,
  execution_id, lifecycle_id,
  client_order_id, broker_order_id, exchange_order_id ou fill_id.

Shadow-stage contract:

- shadow_stage é campo não operacional com valores permitidos exatamente
  PRE_DECISION e POST_DECISION.
- shadow_stage não é execution_mode, lifecycle_state, registry_mode, estado de
  lifecycle de execução nem transição de modo de Registry.

V2.7A decision-request additions:

- PRE_DECISION may carry factual decision_request_id only after a real
  evaluation request is created. Association with V2.7A identity requires the
  durable CLAIMED boundary in section 4.3A.3B. PRE_DECISION has no decision_id.
- POST_DECISION requires the same factual signal_id and, where V2.7A decision
  identity is claimed, the same factual decision_request_id as paired
  PRE_DECISION plus a valid durable COMPLETED record.
- POST_DECISION requires non-empty factual decision_id, decision provenance,
  exact record/request/signal binding, and no identity failure/conflict status.
- Claim or record write failure, claim conflict, incomplete claim, corruption,
  missing replay record, or binding mismatch remains identity-unavailable for
  V2.7A: it cannot be repaired by new ID, legacy fallback, or symbol/side
  matching.
- All existing VERIFY prohibitions remain: no operational execution_id or
  lifecycle_id; no client/broker/exchange/fill identity; no Registry execution;
  no broker/exchange call attributable to V2.7A/V2.8 identity observation; and
  no execution authority.


Position-side observational precedence for V2.7A/V2.8:

1. If explicit sig.get("positionSide") is non-empty, preserve that value.
2. Otherwise, if explicit sig.get("position_side") is non-empty, preserve that
   value.
3. Otherwise, use sig.get("side"), the existing economic-side fallback exactly
   as Falcon V1 already does.

This fallback preserves existing Falcon semantics. It is not new V2 identity,
ownership, broker, market, or position inference. The observer does not use a
broker/market position to determine position side. The selected value is
preserved verbatim: it is not silently normalized, validated into another
side, or converted from BOTH/NET to LONG/SHORT. If positionSide and
position_side are both explicit, non-empty, and contradictory, positionSide
remains selected by existing precedence, while the other raw value and the
fact of contradiction remain visible in observational provenance. Neither raw
explicit value is overwritten. Position-side fields never establish Central,
broker-position, or manual/external ownership.

Owner-plan provenance for V2.7A/V2.8:

owner_type=CENTRAL may be asserted only when the actual Falcon signal/plan
origin factually establishes Central/Falcon plan provenance. That assertion
means only that the candidate plan originated in the Central/Falcon planning
path. It does not mean a BingX position is Falcon-owned, a manual/external
position is adopted, or symbol/side matching proves ownership. Explicit
MANUAL_EXTERNAL or EXTERNAL evidence is never overwritten by contextual
CENTRAL plan provenance. If factual Central plan provenance cannot be
established at the chosen seam, owner_type remains missing or unknown and is
not fabricated.

PRE_DECISION MUST satisfy all of the following:

- shadow_stage=PRE_DECISION;
- factual canonical signal_id, setup, symbol, and economic side are present;
- decision_id is absent or None;
- position-side selection follows the exact V1 precedence above, including raw
  explicit-conflict visibility;
- owner provenance follows the owner-plan rule above;
- Falcon VERIFY safe gates are factual and real trading remains off;
- execution_id and lifecycle_id are absent or None;
- no client, broker, exchange, fill, or other physical/strong identity is
  fabricated;
- no Registry execution is created or mutated; and
- the observer causes no broker or exchange call.

POST_DECISION MUST satisfy all of the following:

- shadow_stage=POST_DECISION;
- the exact same factual signal_id, material plan facts, selected position-side
  observation, raw position-side provenance, and owner-plan provenance as its
  paired PRE_DECISION observation;
- non-empty factual decision_id and decision provenance;
- a completed factual ALLOW or DENY decision result;
- factual decision-to-signal correlation proof for that exact signal_id;
- every VERIFY non-execution rule in PRE_DECISION;
- execution_id and lifecycle_id absent or None; and
- no fabricated physical or strong identity.

If signal/plan facts, selected/raw position-side facts, or justified owner
provenance materially change, the observations are distinct factual plans. A
decision result belonging to a distinct or stale reentry is a correlation
conflict, not a POST_DECISION enrichment.

LEGACY:
- se um registro legado possui lifecycle_id forte, o mesmo valor torna-se execution_id físico na projection V2, sem regenerar.
- se somente client/broker IDs fortes existem, o registro permanece V1 archive/read-only até reconciliação; synthetic legacy identity, se usada em audit, é marcada não factual e não é elegível LIVE.
- um legacy lifecycle value fora do formato exec_<uuid4> é válido como LEGACY_IDENTITY_FORMAT; formato novo não é exigido retroativamente.

5.3 State machine de execução

Estados:
- ENTRY_INTENT: identity durável criada antes do submit.
- ENTRY_PENDING_RECONCILIATION: submit/ACK perdido ou identificação entry incompleta.
- OPEN: entrada identificada e sob gestão permitida.
- PARTIALLY_CLOSED: remaining_qty factual positivo após parcial.
- CLOSE_PENDING_RECONCILIATION: close/broker-flat observado, porém evidência financeira/factual incompleta.
- CLOSED_PROVISIONAL: full close factual, com fee/funding/detalhe pendente.
- CLOSED_RECONCILED: full close e economia reconciliados.
- QUARANTINED: conflito/corrupção/ownership/mode/migration; sem automação.

Transições são monotônicas. CLOSED_PROVISIONAL/CLOSED_RECONCILED nunca voltam a OPEN. QUARANTINED só é resolvido por recovery/reconciliation explícita, registrada em journal.

10. IDEMPOTENCY AUTHORITY

10.1 Autoridade única

A única autoridade de idempotência V2 é registry_v2_events.jsonl com transition EVENT_COMMITTED válida na cadeia de journal. operation_ledger em registry_v2.json é DERIVED CACHE/PROJECTION, não autoridade.

Se ledger e journal divergem:
- journal EVENT_COMMITTED vence para saber se a operation ocorreu;
- Registry entra em diagnostic/rebuild antes de qualquer nova mutation se ledger não puder ser reconstruído consistentemente;
- snapshot row state é verificado contra event payload/digests;
- nenhum caller usa ledger sozinho para responder idempotência.

10.2 Chave de operação

operation_key = operation + execution_id + idempotency_key.

Cada operação contém request_digest canônico, event_id único, expected_generation, expected identity e full mutation payload.

| Operação | Idempotency key | Resultado de retry idêntico | Resultado de retry divergente |
| --- | --- | --- | --- |
| REGISTER | execution intent key | resultado committed original | REGISTRY_IDEMPOTENCY_KEY_CONFLICT |
| UPDATE | source event/management key | patch original não reaplicado | REGISTRY_IDEMPOTENCY_KEY_CONFLICT |
| PARTIAL_CLOSE | close_event_id | parcial original | REGISTRY_CLOSE_EVENT_CONFLICT |
| FULL_CLOSE | close_event_id | close original | REGISTRY_CLOSE_EVENT_CONFLICT |
| RECONCILIATION | reconciliation event + evidence digest | reconciliação original | REGISTRY_RECONCILIATION_CONFLICT |
| QUARANTINE | conflict event ID | estado de quarantine original | REGISTRY_IDEMPOTENCY_KEY_CONFLICT |
| MODE_CONFLICT | mode evidence event ID | conflito original | REGISTRY_IDEMPOTENCY_KEY_CONFLICT |

10.3 Retenção

Close event IDs, reconciliation evidence IDs e outcomes factuais permanecem nas rows. Journal compaction só é permitida por JOURNAL_CHECKPOINT EVENT_COMMITTED que preserva digest/cursor da autoridade anterior. operation_ledger pode ser descartado/reconstruído sem alterar a resposta idempotente.

- idempotency_key;
- request_digest;

11.3 Estados e protocolo

EVENT_PREPARED:
- sob lock exclusivo, validar journal/snapshot/ledger cache.
- atribuir event_seq monotônico.
- append PREPARED e fsync journal.
- nenhum row mudou; nenhum sucesso é retornado.

SNAPSHOT_COMMITTED:
- construir candidato exclusivamente do PREPARED.
- validar identity, invariants, indexes, base generation/digest.
- escrever temp único no mesmo filesystem, flush/fsync, atomic replace e fsync diretório quando suportado.
- o snapshot publicado contém generation=target_generation, wal.materialized_event_id, wal.materialized_seq, wal.materialized_request_digest e after_digest.
- esse witness é o próprio marcador SNAPSHOT_COMMITTED; não existe marcador separado depois do replace.

EVENT_COMMITTED:
- append commit marker no journal e fsync.
- a partir deste ponto o journal responde idempotência.
- ledger cache pode ser atualizado em snapshot posterior ou rebuild; sua defasagem não reduz a autoridade do journal.

Writer fica bloqueado enquanto houver PREPARED não terminal ou recovery pendente. Sucesso é devolvido somente após EVENT_COMMITTED fsync.

11.4 Recovery table

| Caso | Estado/autoridade | Replay | Generation esperada | Mutation committed? | Safe retry | Writable? | Manual recovery? |
| --- | --- | --- | --- | --- | --- | --- | --- |
| A. crash antes de EVENT_PREPARED | snapshot G, journal committed N | não | G | não | executar operação nova | sim | não |
| B. crash depois de EVENT_PREPARED | PREPARED N+1 + snapshot G/N | replay exato do payload se base G/digest coincidir | G+1 após replay | não até commit | REGISTRY_WAL_PREPARED_RECOVERY_REQUIRED; depois resultado idempotente | não até recovery | só se base divergir |
| C. crash durante temp snapshot | PREPARED N+1, temp incompleto, snapshot G/N | descartar temp não publicado e replay | G+1 após replay | não | igual B | não até recovery | só se temp/snapshot inválido |
| D. crash após fsync temp antes de replace | PREPARED N+1, temp válido não publicado, snapshot G/N | temp não é autoridade; replay do PREPARED | G+1 após replay | não | igual B | não até recovery | não se base válido |
| E. crash após replace antes de marcar SNAPSHOT_COMMITTED | estado não é válido pelo protocolo; snapshot publicado deve conter witness | não automático | indeterminada se witness ausente | não | REGISTRY_WAL_SNAPSHOT_RECOVERY_REQUIRED | não | sim; snapshot sem witness é corrupção |
| F. crash depois de SNAPSHOT_COMMITTED | PREPARED N+1 + snapshot G+1 witness/after digest | não reaplicar; finalizar journal commit | G+1 | ainda não externamente committed | REGISTRY_WAL_EVENT_COMMIT_REQUIRED; depois idempotente | não até finalização | só se digests divergem |
| G. crash antes de EVENT_COMMITTED fsync | PREPARED N+1 + snapshot G+1; COMMITTED ausente/parcial | validar/truncar tail inválida e append commit | G+1 | não antes de fsync | igual F | não até finalização | só se journal tail não recuperável |
| H. crash depois de EVENT_COMMITTED | journal committed N+1 + snapshot G+1 | não | G+1 | sim | resultado original idempotente | sim após validação | não |
| I. journal append/fsync failure | journal tail é autoridade somente se record completo/checksummed | não aplicar sem PREPARED fsync; se snapshot witness já existe, finalizar somente após journal recovery | G ou G+1 conforme witness | não até commit fsync | REGISTRY_JOURNAL_WRITE_FAILED/RECOVERY_REQUIRED | não | se chain não puder validar |
| J. snapshot fsync failure | PREPARED válido + snapshot anterior G | replay após recuperar storage | G+1 somente após publish válido | não | PREPARED_RECOVERY_REQUIRED | não | se storage não recuperável |
| K. checksum failure | snapshot/journal com checksum inválido | somente de backup + chain validada | último generation validado | depende de prova | REGISTRY_JOURNAL_CORRUPT ou REGISTRY_JOURNAL_SNAPSHOT_DIVERGENCE | não | sim se não houver cadeia válida |
| L. duplicated EVENT_PREPARED after restart | PREPARED igual por event_id/key/digest | não criar outro; recuperar o existente | target original | não até commit | PREPARED_RECOVERY_REQUIRED; depois idempotente | não até recovery | divergente exige manual/conflict |

11.5 No double apply

- event_seq e event_id são únicos.
- snapshot witness impede aplicar PREPARED já materializado.
- replay só ocorre se snapshot ainda está no base_generation/base_digest esperado.
- snapshot com witness compatível recebe somente EVENT_COMMITTED, sem reaplicar patch.
- event payload é determinístico e não consulta mercado durante replay.
- PREPARED duplicado igual é o mesmo event; divergente é conflito.
- journal committed/checkpoint é a única resposta para idempotência.
- qualquer prova incompleta bloqueia writes, em vez de escolher first/latest.

12. CONCURRENCY

V2 é single-writer por Registry document com lock intra-processo e lock interprocesso. Cada writer:
1. obtém lock com timeout;
2. valida journal chain/snapshot;
3. resolve idempotência no journal committed;
4. executa o WAL protocol;
5. libera lock somente após EVENT_COMMITTED ou estado recovery bloqueado.

Readers usam snapshot validado/read-only e nunca criam/migram arquivos. Temp files têm nome único por process/thread/random, ficam no mesmo filesystem e não são source de truth.

Concorrência esperada:
- same execution + same digest: um commit; outro retorna idempotente.
- same execution + divergent digest: conflict.
- different execution + same client/broker/fill ID: conflito em índice único.
- same logical id + execution diferente: ambas criadas normalmente.
- simultaneous close same event: um commit; outro idempotente ou conflict.
- lock timeout: REGISTRY_PERSISTENCE_LOCK_TIMEOUT, sem bypass.
- outro processo nunca pode ignorar PREPARED pendente.

13. MANUAL/EXTERNAL

MANUAL_EXTERNAL é external observation read-only, não execution Central.

external_observations possui:
- external_observation_id;
- owner_type=MANUAL_EXTERNAL;
- broker_position_id e/ou ordem/fill factual quando disponível;
- symbol, side, position_side, observed_qty, observed_entry;
- observed_at, source, confidence;
- matching_result;
- managed_by_central=false;
- counts_for_falcon_own_limit=false.

Proibições:
- não inferir Falcon por symbol+side;
- não consumir slot Falcon por default;
- não receber stop Falcon;
- não ser fechada/alterada pela Central;
- não fornecer fill para Falcon;
- não compartilhar execution_id/lifecycle_id Central;
- não passar por register/update/close execution API;
- matching de mercado não prova ownership; somente IDs fortes podem produzir relação de evidência e ainda assim não adotam posição.

owner_type UNKNOWN é somente quarantine/diagnóstico; não promove a CENTRAL automaticamente.

14. PAPER/VERIFY/LIVE

14.1 Modos

execution_mode: intenção PAPER, VERIFY ou LIVE.
registry_mode: classificação factual PAPER, REAL, VERIFY, SYNC_ONLY, UNKNOWN ou CONFLICT.
source_mode: claim bruto do produtor.
mode_evidence: fatos e claims versionados.
mode_verified: boolean factual.
mode_conflict: boolean.

14.2 Precedência

1. Evidência factual broker confirmada: ACK de ordem, fill, position/order reconciliation.
2. Configuração explícita LIVE.
3. Configuração PAPER/VERIFY somente quando não existe evidência broker contraditória.
4. Nome do bot, token textual ou heurística são observacionais, nunca identidade factual.

PAPER/VERIFY + evidence REAL não vira LIVE silenciosamente:
- registry_mode=CONFLICT;
- mode_verified=false;
- lifecycle_state=QUARANTINED ou ENTRY_PENDING_RECONCILIATION;
- REGISTRY_MODE_CONFLICT;
- sem gestão/learning financeiro automático até reconciliation.

LIVE sem ACK/fill não é REAL automaticamente: execution_mode=LIVE, registry_mode=UNKNOWN/VERIFY conforme evidência, estado ENTRY_INTENT/ENTRY_PENDING_RECONCILIATION. Depois de ACK/fill válido, registry_mode=REAL.

14.3 Isolation

VERIFY não cria execution Registry. PAPER cria execution simulada Central. LIVE requer full identity/intent antes de broker. Analytics segmenta PAPER/REAL. Nenhum modo de uma execution é convertido para outro; uma nova execution é criada se o plano mudar de VERIFY para PAPER/LIVE.

15. LEGACY READ-ONLY VIEW

15.1 Definição

legacy_projection é função/view derivada de snapshot V2 committed. Não é segunda store, não é authority e não substitui archive V1.

Forma preferida on-demand:
- logical_trade_id;
- execution_ids;
- status UNIQUE, AMBIGUOUS, NOT_FOUND ou LEGACY_ARCHIVED;
- row projection somente se UNIQUE e para leitura;
- source_generation, source_snapshot_id, source_digest, projection_version.

15.2 Cache opcional

Se materializada, a view usa arquivo separado:
registry_v2_legacy_projection.json.

É cache descartável:
- contém projection_digest e source snapshot/generation/digest;
- mismatch com V2 invalida e descarta cache;
- sobrevive restart somente como cache validável;
- não é backup, journal, migration source ou mutation source;
- nunca usa o nome/path do trade_registry.json V1 original.

15.3 Consumers

- Consumers novos operacionais usam V2 directly.
- Adapters legados usam projection exclusivamente para READ compatibility.
- V1 logical selector com N rows retorna AMBIGUOUS; não escolhe first/latest.
- Nenhum register/update/close/reconcile recebe ou lê projection como authority.
- Após cutover, V1 original é ARCHIVE/READ_ONLY. Não recebe dados de V2 e não é sobrescrito.

16. MIGRATION

16.1 Estratégia

Migração SIDE_BY_SIDE. V1 original permanece preservado; V2 usa snapshot/journal próprios. Não há in-place migration, dual-write independente ou rewrite massivo de closed history.

16.2 Fases lógicas

PHASE 0 — READ-ONLY AUDIT:
capturar hashes, tamanhos e contagens V1; classificar rows por IDs fortes, ambiguidade, ausência e conflito.

PHASE 1 — DORMANT V2:
schema/helpers/readers sem writer runtime.

PHASE 2 — DUAL-READ:
comparar V1/V2 read-only, sem mutar ambos.

PHASE 3 — PROPOSED MIGRATION AUDIT:
gerar plano de rows inequívocas, legacy archive e quarantine; não publica Registry V2 operacional.

PHASE 4 — V2 PRIMARY PAPER:
somente V2.9, PAPER isolado e autorizado; V1 permanece read-only.

PHASE 5 — LEGACY READ-ONLY:
V1 apenas archive/compatibilidade, sem novos writers.

PHASE 6 — FUTURE LIVE PILOT:
fora V2.0–V2.10, sujeito ao gate da seção 28.

16.3 Identidade legada

- Legacy row com lifecycle_id forte: execution_id recebe exatamente esse valor; lifecycle alias é igual.
- Legacy row com aliases fortes conflitantes: QUARANTINED; nenhuma projection operacional.
- Legacy row sem lifecycle mas com client/broker evidence: archive/read-only até reconciliation.
- Synthetic legacy audit ID somente em relatório/projection auditável, formato legacyaudit_<sha256 de arquivo+collection key+raw digest>; nunca é apresentado como factual broker/lifecycle, nem gerenciável LIVE.
- closed history não é reescrito; views carregam source reference/digest.
- symbol/side nunca resolve legacy identity.

17. PERSISTENCE

17.1 Escolha

KEEP_JSON nesta fase, pois o problema P0 é identity correctness, não evidência de necessidade de banco novo. JSON V2 é aceitável somente com WAL, lock interprocesso, checksums, backups, generation e recovery definidos nesta SPEC.

17.2 Requisitos

- directory persistente configurado;
- temp file único no mesmo filesystem;
- flush/fsync arquivo e diretório quando suportado;
- atomic replace;
- lock interprocesso e local;
- snapshot_digest SHA-256;
- generation monotônica;
- journal event_seq monotônico;
- backups/manifests antes de publish/migration;
- read-only loader sem criação/migração;
- limites de tamanho/retenção;
- compaction por checkpoint committed;
- recovery fail-closed.

17.3 Quando replatform considerar

Abrir RFC separado para SQLite/Postgres somente se houver múltiplos writers distribuídos, snapshot exceder SLA de lock/rebuild, transações cruzadas forem necessárias ou houver falha repetida de atomicidade no volume persistente. Não replatform neste refactor.

20. FALCON CONTRACT

Falcon V2 usa o único caminho existente:
Signal -> Decision/Risk -> Execution Orchestrator -> Registry intent -> Broker -> Lifecycle/management -> Reconciliation.

Requisitos Falcon LIVE V2:
- signal_id;
- decision_id;
- execution_id=lifecycle_id;
- execution intent idempotency key;
- client_order_id antes de submit;
- exact symbol, side e position_side;
- owner_type=CENTRAL;
- disaster stop plan/identity;
- expected identity em update/close;
- broker order ID após ACK;
- fill IDs quando disponíveis.

Sequência:
1. Orchestrator cria ID único antes do broker.
2. Registry commit de ENTRY_INTENT é pré-condição para submit.
3. client_order_id é reservado sob essa identity.
4. ACK perdido entra em ENTRY_PENDING_RECONCILIATION e é reconciliado por client/order/fill; não reenvia cegamente.
5. Disaster stop pertence à mesma identity e deve ser confirmado antes de gestão normal.
6. TP50, BE/trailing e runner atualizam somente execution exata.
7. Terminal recovery e real_close_reconciliation localizam execution pelo ID único, depois client/broker/fill; nunca market fields.
8. Manual/external same leg gera awareness/conflict, não ownership Falcon.
9. Registry/History/Journal carregam execution_id e lifecycle_id alias igual.
10. Não há segundo executor, não há média agregada BingX como truth do Falcon.

O fallback atual que constrói lifecycle a partir de client/order depois do ACK é legado V1 e não satisfaz V2. No V2.LIVE-PILOT ele deve estar removido/inacessível no caminho novo, pois V2 ID nasce antes de broker invocation.

Prioridade de locator:
1. execution_id/lifecycle_id único;
2. client_order_id;
3. broker/exchange order ID;
4. fill IDs;
5. legacy read-only único, nunca para mutation LIVE.

- journal corruption without valid chain;
